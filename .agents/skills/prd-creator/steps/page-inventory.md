# Report pages (page inventory)

A Power BI report is organized as a set of **report pages**, each supporting a user journey or decision. This phase locks the list of pages — the report's equivalent of "top-level features." Drill-through and tooltip pages count as pages too, because each needs designing and building, even though nobody opens them from a tab.

Propose a list of **3–7 pages** that together deliver the core purpose. Derive them from the user journeys: ask (or infer) "what are the main questions or tasks the report supports?" and turn each into a page. Present them as a numbered list in chat, each with a one-line description of its purpose and the decision it serves, and **name the user each page belongs to**: one user from the locked Users list, the one who mainly uses it. A page everyone opens goes under the user who drives it (an executive summary belongs to the executives, even though analysts read it too).

Then ask the user (via AskUserQuestion or free text) which to keep, which to cut, what's missing, and whether any page sits under the wrong user. Keep the set focused — a tight, well-sequenced handful of pages beats a sprawling one.

The output of this phase is a **locked page inventory, ordered by development priority** (the order also drives the milestone sequence later), with each page assigned to one user. The PRD's in-scope section is grouped by user, so if a user ends up with no pages, raise it: either a page is missing or that user is not really a user of this report. Lock it before moving on.
